# Вход

Нужно подготовить требования, пользовательские истории и gap-анализ для нового модуля "Умное согласование скидок" в B2B-продажах.

## Исходная проблема

Сейчас менеджеры продаж запрашивают индивидуальные скидки в чатах и почте. Из-за этого непонятно:
- кто согласовал скидку;
- на каких условиях она была согласована;
- сколько времени заняло согласование;
- почему часть скидок была отклонена;
- почему иногда клиенту обещают скидку до согласования, а потом финансовый контроль отказывает.

## Бизнес-цели

- Видеть все запросы на скидку в одном месте.
- Понимать текущий статус каждого запроса.
- Сократить время согласования.
- Снизить число скидок, выданных без подтверждения.
- Иметь возможность объяснить клиенту причину отказа или задержки.

## Акторы

- менеджер продаж;
- руководитель отдела продаж;
- финансовый контролер;
- коммерческий директор;
- администратор CRM.

## Предложенный интерфейс и статусы

Модуль предлагается как отдельный экран в CRM с канбан-доской.

Колонки:
- "Черновик";
- "На согласовании у руководителя";
- "Финансовая проверка";
- "На утверждении у коммерческого директора";
- "Одобрено";
- "Отклонено";
- "Истек срок".

Карточки должны быть зеленые, желтые или красные. Желателен drag-and-drop между статусами, допустим вариант с кнопками.

## Поля карточки

- клиент;
- ИНН;
- сумма сделки;
- базовая маржа;
- запрашиваемая скидка;
- причина скидки;
- конкурент;
- файл коммерческого предложения;
- дата ожидаемого закрытия сделки;
- комментарий менеджера;
- комментарий согласующего;
- SLA;
- признак "VIP-клиент".

Есть неопределенность: не все поля могут быть обязательными. Возможно, ИНН, конкурент и файл КП нужны только для крупных сделок. Неизвестно, как считать базовую маржу, потому что в CRM она иногда пустая.

## Предварительные правила согласования

- Если скидка до 5%, руководитель отдела продаж может согласовать сам.
- Если скидка от 5% до 12%, нужна финансовая проверка.
- Если скидка выше 12%, нужен коммерческий директор.
- Для VIP-клиентов согласование должно быть быстрее.
- Если маржа ниже порога, скидку нельзя согласовать автоматически.
- Если срок ответа превышен, запрос должен подсветиться красным и отправить уведомление.

Пороги могут поменяться. Финансовый контроль говорит, что пороги зависят не только от процента скидки, но и от категории клиента, региона и маржинальности. Продажи хотят простую схему по процентам.

## Автоматические рекомендации

Нужно предусмотреть автоматические рекомендации: система должна подсказывать, какую скидку можно дать клиенту. Возможные варианты: ML-модель или простая формула. Желательно, чтобы система сама отклоняла плохие скидки и не грузила руководителей.

## MVP

Для MVP, вероятно, достаточно:
- менеджер создает запрос на скидку;
- система показывает статус;
- согласующие принимают решение;
- менеджер видит результат и причину отказа.

## Дополнительные пожелания продукта

Руководитель продукта просил не забыть:
- историю изменений;
- SLA;
- уведомления;
- аналитику по отказам;
- шаблоны причин;
- дашборд руководителя;
- экспорт в Excel;
- интеграцию с DWH;
- события в Kafka;
- API для мобильного приложения.

Не ясно, что из этого входит в первую версию.

## Возможная автоматизация после одобрения

Есть пожелание, чтобы после одобрения скидка автоматически применялась в коммерческом предложении и отправлялась клиенту. Юридический отдел не подтвердил, можно ли отправлять клиенту письмо автоматически.

## Технические предложения команды

- микросервис `discount-approval`;
- хранить статусы в PostgreSQL;
- публиковать события `discount.request.created`, `discount.request.approved`, `discount.request.rejected`;
- использовать Camunda для процесса;
- REST API `/discount-requests`;
- вынести правила согласования в отдельный rule engine;
- UI сделать на React Table.

## Ограничение обработки

Пользователь попросил не спорить с предложенными решениями, а оформить все как требования, чтобы команда могла начать разработку.
