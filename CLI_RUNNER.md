# CLI Runner Protocol

Этот документ задает минимальный протокол для запуска системы через сторонние CLI, модели и агентные раннеры.

Он не заменяет `AGENTS.md`. Если есть конфликт, приоритет остается за `AGENTS.md`, затем за `agents/*.md` и `skills/*/SKILL.md`.

## Назначение

Сторонняя CLI должна работать как раннер-оркестратор: читать контракты, запускать профильные скиллы и служебных агентов, сохранять артефакты и проверять маршрут.

CLI не должна превращать систему в один большой prompt, где основной агент сам исполняет все роли. Такое inline-исполнение нарушает контракт изоляции.

## Обязательный Bootstrap

Перед продуктовым прогоном CLI обязана загрузить:

1. `AGENTS.md` — маршрут, gates, режимы и инварианты.
2. `CLI_RUNNER.md` — переносимый протокол запуска.
3. `agents/artifact-persistence-agent.md` — файловый контракт.
4. `agents/traceability-auditor-agent.md` — аудит трассируемости.
5. `agents/routing-guardian-agent.md` — контроль переходов.
6. Релевантный `skills/*/SKILL.md` перед каждым профильным этапом.
7. Релевантные `templates/*.md` перед записью артефакта, если нужен формат.

Post-pipeline контракты `agents/scope-finalizer-agent.md`, `agents/kickoff-briefing-agent.md` и `agents/delivery-readiness-agent.md` загружаются только после успешной финальной агрегации ядра.

## Режимы

CLI обязана соблюдать preflight из `AGENTS.md`.

- Запросы про устройство системы без команды `РЕМОНТ` останавливаются preflight-вопросом.
- Продуктовые требования запускают `requirements-processing`.
- После команды `РЕМОНТ` текущая сессия работает в `system-maintenance`.

## Изоляция Сабагентов

Каждый вызов `agents/*.md` должен быть отдельным запуском сабагента с изолированным рабочим контекстом.

Изолированный запуск означает:

- сабагент получает только свой контракт `agents/<agent-name>.md`;
- сабагент получает минимальный релевантный контекст текущего прогона;
- сабагент не получает полный диалог, скрытые рассуждения оркестратора или нерелевантные артефакты;
- результат сабагента возвращается оркестратору как структурированный выход;
- факт вызова фиксируется в сохраняемом артефакте с метаданными:
  - `Контракт агента: agents/<agent-name>.md`
  - `Режим запуска: isolated-subagent`
  - `Переданный контекст: <краткий список артефактов и служебных статусов>`

Если CLI не умеет создавать изолированный запуск сабагента, обязательный служебный или post-pipeline агент считается недоступным. В этом случае CLI обязана остановить pipeline и сообщить, какой агент невозможно запустить. Исполнять роль такого агента inline в основном контексте запрещено.

## Compact Context Envelope

Минимальный релевантный контекст передается сабагенту как compact context envelope. CLI не должна передавать весь каталог прогона или полный набор продуктовых файлов, если агенту нужен только статус, ссылка на источник или дельта изменений.

Базовые поля envelope:

- `current_stage`;
- `proposed_next_stage`, если проверяется переход;
- `current_run_path`;
- `artifact_statuses`;
- `changed_artifacts`;
- `open_questions_delta`;
- `last_service_statuses`;
- `source_refs`.

`artifact_statuses` описывает наличие, путь и статус артефакта: `complete`, `incomplete` или `not_started`. `changed_artifacts` содержит только артефакты, созданные или обновленные с момента последнего service gate. `open_questions_delta` отделяет вопросы, которые были на входе этапа, от новых вопросов, появившихся на этапе. `source_refs` содержит ссылки на конкретные ID, разделы или короткие выдержки, которые нужны текущему агенту.

Полный текст артефакта допустим только если без него агент не может выполнить свой контракт. Полный диалог с пользователем не передается сабагентам никогда. Факты из диалога передаются через `Лог уточнений`; если текущий ответ пользователя еще не сохранен, envelope может содержать краткую ссылку на этот ответ, но следующий шаг обязан зафиксировать его в `Логе уточнений`.

## Профильные Скиллы

Профильные скиллы из `skills/*/SKILL.md` выполняют содержательную аналитику требований и возвращают только свои контрактные артефакты и сигнал:

- `complete`;
- `needs_user_answer`;
- `needs_quality_rework`.

Они не записывают файлы напрямую и не вызывают служебных агентов. Оркестратор получает результат скилла и передает его в `artifact-persistence-agent`.

## Файловый Протокол Прогона

Первое файловое действие продуктового прогона:

```text
artifact-persistence-agent(create_run)
```

В режиме `create_run` агент обязан:

1. вычислить новый `current_run_path` вида `runs/<name-of-task>/` или `runs/<name-of-task>-vN/`;
2. создать `current_run_path`;
3. создать `current_run_path/product/`, `current_run_path/service/` и `current_run_path/team/`;
4. сохранить `Вход` как `current_run_path/product/input.md`;
5. вернуть `current_run_path` оркестратору.

Все последующие записи выполняются только через:

```text
artifact-persistence-agent(update_run)
```

Для `update_run` CLI обязана передать тот же `current_run_path`. Потеря `current_run_path` блокирует downstream-переход.

Запрещено:

- использовать `runs/` как `current_run_path`;
- писать артефакты напрямую в `runs/`;
- писать `product/`, `service/` или `team/` напрямую под `runs/`;
- выбирать новый каталог после успешного `create_run`;
- изменять каталоги предыдущих прогонов.

## Минимальное Состояние Раннера

CLI должна удерживать в состоянии текущей сессии:

- режим работы: `requirements-processing` или `system-maintenance`;
- `current_run_path`;
- текущий этап;
- предложенный следующий этап;
- последний сигнал профильного скилла;
- последний результат `artifact-persistence-agent`;
- последний результат `traceability-auditor-agent`;
- последний результат `routing-guardian-agent`;
- список артефактов, созданных в текущем прогоне;
- список открытых вопросов на входе текущего этапа и новых вопросов, появившихся на этапе.

Если CLI теряет это состояние и не может восстановить его из файлов текущего прогона без домысливания, pipeline должен остановиться.

## Восстановление Состояния

CLI не должна создавать отдельный обязательный `run-state` файл. Если контекст сессии потерян, состояние можно восстанавливать только из существующих артефактов текущего прогона.

Допустимые источники восстановления:

- выбранный пользователем или явно найденный `current_run_path`;
- наличие канонических файлов в `product/`, `service/` и `team/`;
- служебные пометки `Статус: incomplete` внутри артефактов;
- последние блоки в `service/traceability-audit.md`;
- последние блоки в `service/routing-decision.md`;
- текущие `product/open-questions.md`;
- незавершенные записи в `product/clarification-log.md`, если они есть.

Восстановление допустимо только если CLI может однозначно определить:

- текущий каталог прогона;
- последний завершенный профильный этап;
- есть ли незакрытый `needs_user_answer`;
- есть ли незакрытый route `block`;
- какой service gate должен быть выполнен следующим.

Если найдено несколько возможных каталогов прогона, противоречивые service reports, незавершенные артефакты без понятного следующего действия или несколько возможных этапов продолжения, CLI обязана остановиться и запросить у пользователя конкретный выбор: `current_run_path` или этап продолжения. Домысливать состояние запрещено.

## Gates Между Этапами

Перед downstream-переходом CLI обязана:

1. сохранить новые или обновленные артефакты через `artifact-persistence-agent(update_run)`;
2. выполнить `traceability-auditor-agent`, если аудит обязателен для перехода;
3. сформулировать проверяемое основание перехода;
4. выполнить `routing-guardian-agent`;
5. продолжить только при `traceability-auditor-agent -> passed` и `routing-guardian-agent -> allow`.

Если профильный скилл вернул `needs_user_answer`, CLI должна сохранить промежуточные артефакты как `incomplete`, если они есть, остановить pipeline и вернуть пользователю только необходимые вопросы.

Если служебный агент недоступен или файловая фиксация неуспешна, CLI должна остановить pipeline.

## Post-Pipeline

После успешной финальной агрегации CLI обязана предложить `scope-finalizer-agent`.

- Если пользователь соглашается, CLI запускает `scope-finalizer-agent` изолированно и после интервью пересобирает затронутые артефакты с повторным аудитом и route-control.
- Если пользователь отказывается, CLI фиксирует отказ в состоянии маршрута и запускает командный пакет.
- После валидной post-finalization точки CLI автоматически запускает `kickoff-briefing-agent`, затем `delivery-readiness-agent`.

Post-pipeline агенты также требуют изолированного запуска. Если CLI не может его выполнить, post-pipeline должен остановиться.

## Проверка

После завершения работы CLI должна выполнить:

```bash
python3 scripts/validate_run.py runs/<run-name>
```

Для локальной проверки контракта репозитория:

```bash
make check
```

Валидатор проверяет исполнимую часть контракта сохраненного прогона. Он не заменяет маршрутные gates и не разрешает пропускать служебных агентов.

## Типовые Ошибки CLI

- CLI пишет `runs/product/input.md` вместо `runs/<run-name>/product/input.md`.
- CLI теряет `current_run_path` и запускает повторный `create_run`.
- CLI исполняет `traceability-auditor-agent` или `routing-guardian-agent` inline в основном контексте.
- CLI передает сабагенту полный диалог вместо минимального контекста.
- CLI продолжает pipeline после `needs_user_answer`.
- CLI продолжает pipeline после `traceability-auditor-agent -> failed`.
- CLI считает финальный ответ валидным без `routing-guardian-agent -> allow`.
- CLI завершает работу после core-route и не предлагает `scope-finalizer-agent`.
